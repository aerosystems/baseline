## Як обрати операційну систему?

Уявіть: ви — системний адміністратор у банку. Потрібно обрати ОС для серверів, які обробляють фінансові транзакції. Що важливіше: швидкість чи надійність? Безпека чи зручність? Як порівнювати Windows Server, Linux, FreeBSD?

Або інша ситуація: ви розробляєте програмне забезпечення для медичного обладнання. Збій може коштувати життя. Які вимоги до ОС тут критичні?

Для обґрунтованого вибору потрібно розуміти **критерії оцінки операційних систем**.

## 1. Надійність (Reliability)

**Надійність** — здатність системи працювати коректно протягом тривалого часу без збоїв.

### Ключові аспекти надійності

**Стабільність** — система не "падає" без причини.

```
Типовий uptime серверів:
┌─────────────────────────────────────────┐
│ Windows Server   │ 99.9% │ ~8.7 год/рік простою
│ Linux (добре     │ 99.99%│ ~52 хв/рік простою
│   налаштований)  │       │
│ Спеціалізовані   │99.999%│ ~5 хв/рік простою
│   системи        │       │
└─────────────────────────────────────────┘
```

**Відмовостійкість** — система продовжує працювати навіть при збоях компонентів.

```
┌─────────────────────────────────────────────────────────┐
│                   Кластер серверів                      │
│  ┌─────────┐   ┌─────────┐   ┌─────────┐               │
│  │ Server1 │   │ Server2 │   │ Server3 │               │
│  │  [OK]   │   │  [FAIL] │   │  [OK]   │               │
│  └────┬────┘   └────┬────┘   └────┬────┘               │
│       │             ✗             │                     │
│       └─────────────┴─────────────┘                     │
│                     │                                   │
│              Load Balancer                              │
│       (перенаправляє трафік на живі ноди)              │
└─────────────────────────────────────────────────────────┘
```

**Ізоляція збоїв** — помилка в одному компоненті не руйнує всю систему.

**Практичний приклад**: Kernel panic vs Application crash

```bash
# Якщо падає звичайна програма — система працює далі
./buggy_program
# Segmentation fault (core dumped)
# Інші програми продовжують працювати

# Якщо падає ядро — система зупиняється
# Kernel panic - not syncing: Fatal exception
# Потрібне перезавантаження
```

**Як Linux забезпечує надійність:**

```bash
# Watchdog — автоматичне перезавантаження при зависанні
cat /proc/sys/kernel/watchdog

# Журнали для діагностики
journalctl -p err -b  # Помилки з останнього завантаження

# Реальний uptime сервера
uptime
# 10:30:01 up 547 days, 3:22, 2 users, load average: 0.15, 0.10, 0.08
```

### Метрики надійності

| Метрика | Визначення | Приклад |
|---------|------------|---------|
| **MTBF** | Mean Time Between Failures | 50,000 годин |
| **MTTR** | Mean Time To Repair | 30 хвилин |
| **Availability** | MTBF / (MTBF + MTTR) | 99.99% |

## 2. Безпека (Security)

**Безпека** — захист системи від несанкціонованого доступу, модифікації та знищення даних.

### Модель безпеки

```
┌────────────────────────────────────────────────────────────┐
│                    ЗОВНІШНІ ЗАГРОЗИ                        │
│    Хакери, віруси, DDoS, фішинг, експлойти                │
└──────────────────────────┬─────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────────┐
│ 1. ПЕРИМЕТР            Firewall, IDS/IPS                  │
├────────────────────────────────────────────────────────────┤
│ 2. АУТЕНТИФІКАЦІЯ      Паролі, 2FA, сертифікати           │
├────────────────────────────────────────────────────────────┤
│ 3. АВТОРИЗАЦІЯ         Права доступу, ролі, ACL           │
├────────────────────────────────────────────────────────────┤
│ 4. ІЗОЛЯЦІЯ            Процеси, контейнери, VM            │
├────────────────────────────────────────────────────────────┤
│ 5. ШИФРУВАННЯ          Дані в спокої та в русі            │
├────────────────────────────────────────────────────────────┤
│ 6. АУДИТ               Логи, моніторинг, алерти           │
└────────────────────────────────────────────────────────────┘
```

### Принцип найменших привілеїв

Програма повинна мати мінімум прав, необхідних для виконання задачі.

**Практичний приклад**: Чому веб-сервер не запускається від root?

```bash
# Погана практика (процес має повні права)
sudo nginx

# Хороша практика (nginx знижує привілеї після старту)
# nginx.conf:
# user www-data;

# Перевірити, від якого користувача працює процес
ps aux | grep nginx
# www-data  1234  0.0  0.1  ... nginx: worker process
```

Якщо хакер знайде вразливість у nginx, він отримає права www-data, а не root.

### Механізми захисту в Linux

```bash
# 1. Права доступу до файлів
ls -la /etc/shadow
# -rw-r----- 1 root shadow 1234 Jan 15 /etc/shadow

# 2. Capabilities — дрібнозернистий контроль привілеїв
getcap /usr/bin/ping
# /usr/bin/ping cap_net_raw=ep

# 3. SELinux / AppArmor — обов'язковий контроль доступу
getenforce  # SELinux: Enforcing, Permissive, Disabled
aa-status   # AppArmor: профілі програм

# 4. Firewall
sudo iptables -L
sudo ufw status

# 5. Аудит
sudo ausearch -m avc -ts recent  # SELinux відмови
```

### Типові вразливості та захист

| Загроза | Опис | Захист ОС |
|---------|------|-----------|
| Buffer overflow | Переповнення буфера | ASLR, Stack Canaries, NX bit |
| Privilege escalation | Підвищення привілеїв | Capabilities, namespaces |
| Rootkit | Приховане шкідливе ПЗ | Secure Boot, IMA |
| Brute force | Підбір паролів | PAM limits, fail2ban |

**Ефективність** — мінімізація накладних витрат та оптимальне використання ресурсів.

### Метрики ефективності

```
┌─────────────────────────────────────────────────────────────┐
│                    ЕФЕКТИВНІСТЬ ОС                          │
│                                                             │
│  Throughput          Скільки задач за одиницю часу          │
│  ─────────────────────────────────────────────────          │
│  │████████████████████████████████                 │        │
│  └─────────────────────────────────────────────────         │
│                                                             │
│  Latency             Затримка відповіді                     │
│  ─────────────────────────────────────────────────          │
│  │████                                             │        │
│  └─────────────────────────────────────────────────         │
│  (менше = краще)                                            │
│                                                             │
│  CPU Utilization     Використання процесора                 │
│  ─────────────────────────────────────────────────          │
│  │████████████████████████████████████████████████ │ 95%    │
│  └─────────────────────────────────────────────────         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Накладні витрати ОС

Кожна абстракція має ціну:

| Операція | Типова затримка |
|----------|-----------------|
| Системний виклик | 100-1000 нс |
| Перемикання контексту | 1-10 мкс |
| Page fault (пам'ять з диска) | 1-10 мс |
| Мережевий пакет (localhost) | 10-50 мкс |

**Практичний приклад**: Вимірювання вартості системного виклику

```bash
# Скільки викликів getpid() за секунду?
# (getpid — найпростіший syscall)

cat > bench.c << 'EOF'
#include <unistd.h>
#include <stdio.h>
#include <time.h>

int main() {
    struct timespec start, end;
    int iterations = 10000000;

    clock_gettime(CLOCK_MONOTONIC, &start);
    for (int i = 0; i < iterations; i++) {
        getpid();
    }
    clock_gettime(CLOCK_MONOTONIC, &end);

    double elapsed = (end.tv_sec - start.tv_sec) +
                     (end.tv_nsec - start.tv_nsec) / 1e9;
    printf("%.0f syscalls/sec\n", iterations / elapsed);
    printf("%.0f ns per syscall\n", elapsed * 1e9 / iterations);
    return 0;
}
EOF

gcc -O2 bench.c -o bench && ./bench
# Приблизний результат: 5-10 млн syscalls/sec
# 100-200 нс на виклик
```

## 4. Масштабованість (Scalability)

**Масштабованість** — здатність ефективно працювати при збільшенні навантаження або ресурсів.

### Вертикальне масштабування (Scale Up)

Додаємо ресурси до одного сервера:

```
До:                         Після:
┌─────────────────┐         ┌─────────────────┐
│ 4 CPU cores     │         │ 32 CPU cores    │
│ 16 GB RAM       │ ──────→ │ 256 GB RAM      │
│ 500 GB SSD      │         │ 4 TB NVMe       │
└─────────────────┘         └─────────────────┘
```

**Виклик для ОС**: Чи може ядро ефективно використати 256 ядер? Чи працюють алгоритми при 1 ТБ RAM?

### Горизонтальне масштабування (Scale Out)

Додаємо більше серверів:

```
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│ Node 1  │  │ Node 2  │  │ Node 3  │  │ Node 4  │
└────┬────┘  └────┬────┘  └────┬────┘  └────┬────┘
     │            │            │            │
     └────────────┴────────────┴────────────┘
                      │
              Load Balancer / Orchestrator
```

**Практичний приклад**: Linux на різних масштабах

```bash
# Raspberry Pi Zero (512 МБ RAM, 1 core)
cat /proc/cpuinfo | grep -c processor  # 1
free -h                                  # 512M

# Ваш ноутбук (16 ГБ RAM, 8 cores)
cat /proc/cpuinfo | grep -c processor  # 8
free -h                                  # 16G

# Суперкомп'ютер Frontier (9.2 PB RAM, 9,472 nodes)
# Теж Linux!
```

### Тест масштабованості

Як перевірити, чи масштабується програма?

```bash
# Навантажувальне тестування веб-сервера
# (встановіть: apt install apache2-utils)

# 1 потік, 1000 запитів
ab -n 1000 -c 1 http://localhost/

# 100 паралельних потоків, 10000 запитів
ab -n 10000 -c 100 http://localhost/

# Порівняйте requests/sec
# Ідеально: має рости лінійно з кількістю ядер
```

### Як досягається портативність

```

│              Код ядра (архітектурно-незалежний)             │
```

## Практичні сценарії вибору ОС

### Сценарій 1: Веб-сервер для стартапу

**Вимоги:** низька вартість, надійність, масштабованість

**Рішення:** Linux (Ubuntu Server, Debian)
- Безкоштовний
- Uptime 99.99%+
- Легко масштабувати в хмарі (AWS, GCP, Azure)

### Сценарій 2: Робоча станція для розробника

**Вимоги:** зручність, доступ до інструментів, продуктивність

**Рішення:** macOS або Linux
- Нативний термінал (bash/zsh)
- Docker, Git, компілятори
- Сумісність з серверами (теж Linux)

### Сценарій 3: Медичне обладнання

**Вимоги:** максимальна надійність, сертифікація, детермінованість

**Рішення:** QNX або спеціалізований Linux
- Мікроядро = менше коду = менше багів
- Сертифікація для медичних пристроїв
- Real-time гарантії

### Сценарій 4: Банківська система

**Вимоги:** безпека, надійність, аудит

**Рішення:** Linux з SELinux або AIX
- Обов'язковий контроль доступу
- Повний аудит
- Підтримка від вендора

## Практичне завдання

Оцініть характеристики вашої системи:

```bash
# 1. Надійність — як довго працює система?
uptime
cat /proc/loadavg

# 2. Безпека — які механізми захисту активні?
getenforce 2>/dev/null || echo "SELinux not installed"
aa-status 2>/dev/null || echo "AppArmor not installed"
sudo ufw status 2>/dev/null || echo "UFW not installed"

# 3. Ефективність — накладні витрати системи
# Системні процеси vs користувацькі
ps aux | awk '{if($1=="root") sys++; else usr++} END {print "System:", sys, "User:", usr}'

# 4. Архітектура системи
uname -m
cat /proc/cpuinfo | grep "model name" | head -1

# 5. Версія ядра (портативність)
uname -r
cat /proc/version
```

## Підсумок

| Вимога | Що означає | Приклад метрики |
|--------|------------|-----------------|
| **Надійність** | Працює без збоїв | Uptime 99.99% |
| **Безпека** | Захищена від атак | CVE за рік |
| **Ефективність** | Мінімальні накладні витрати | Latency syscall < 1мкс |
| **Масштабованість** | Росте з навантаженням | Лінійний ріст throughput |
| **Портативність** | Працює на різному залізі | Кількість архітектур |
| **Зручність** | Легко використовувати | Час на типову задачу |

**Ключовий висновок:** Не існує "найкращої ОС" — є ОС, оптимальна для конкретної задачі. Розуміння вимог допомагає зробити правильний вибір.
