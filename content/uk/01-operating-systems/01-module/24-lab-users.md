**Мета:** навчитися адмініструвати облікові записи в Linux: створювати й налаштовувати користувачів і групи, керувати правами доступу до файлів символьним і числовим способом, застосовувати спеціальні біти та маску `umask`, налаштовувати спільний каталог для групи й розмежовувати доступ списками ACL.

## Теоретичні відомості

### 1 Обліковий запис як запис у файлі

Користувач у Linux — це насамперед рядок у файлі `/etc/passwd` із числовим ідентифікатором UID, основною групою GID, домашнім каталогом і оболонкою входу. Паролі зберігаються окремо — у `/etc/shadow`, доступному лише для `root`, і не у відкритому вигляді, а як хеш.

```bash
grep student /etc/passwd
# student:x:1000:1000:Student,,,:/home/student:/bin/bash
#    ім'я :x:UID :GID :опис      :домашній      :оболонка
```

Літера `x` на місці пароля означає, що хеш зберігається в `/etc/shadow`. Системні облікові записи мають UID менший за 1000 і зазвичай оболонку `/usr/sbin/nologin`: вони існують для служб, а не для людей.

Таблиця 1 — Файли, що описують облікові записи

| Файл | Що містить | Доступ |
|------|------------|--------|
| `/etc/passwd` | ім'я, UID, GID, домашній каталог, оболонка | читання для всіх |
| `/etc/shadow` | хеш пароля, терміни дії | лише root |
| `/etc/group` | групи та список їхніх учасників | читання для всіх |
| `/etc/skel` | шаблон домашнього каталогу нового користувача | читання для всіх, змінює root |
| `/etc/sudoers` | політика підвищення прав | лише root, редагувати через `visudo` |

### 2 Створення та налаштування користувачів

```bash
sudo adduser dev1                      # інтерактивно: домашній каталог, пароль
sudo useradd -m -s /bin/bash dev2      # низькорівневий аналог
sudo passwd dev2                       # задати пароль
sudo usermod -aG developers dev1       # додати до додаткової групи
sudo usermod -L dev2                   # заблокувати пароль (додає ! перед хешем)
sudo usermod -e 1 dev2                 # і сам обліковий запис: строк дії минув
sudo chage -l dev1                     # терміни дії пароля
sudo deluser --remove-home dev2        # видалити разом із домашнім каталогом
```

Ключ `-a` в `usermod -aG` критично важливий: без нього список додаткових груп не доповнюється, а замінюється, і користувач може втратити, зокрема, членство в групі `sudo`.

Блокування пароля (`usermod -L`) не заважає входити за ключем SSH: перевірка ключа не звертається до хеша в `/etc/shadow`. Щоб справді закрити обліковий запис, додатково роблять його строк дії таким, що минув (`usermod -e 1`), або встановлюють оболонку `/usr/sbin/nologin`.

### 3 Групи: основна й додаткові

Кожен користувач має рівно одну основну групу (її GID записано в `/etc/passwd`) і будь-яку кількість додаткових. Основна група визначає групу-власника новостворених файлів, додаткові — розширюють доступ.

```bash
sudo groupadd developers
sudo groupadd -g 2000 testers          # з явним GID
id dev1                                # усі групи користувача
groups dev1
getent group developers                # склад групи
sudo gpasswd -d dev1 developers        # вилучити з групи
```

Зміна складу груп набуває чинності для нового сеансу: користувач має вийти й увійти знову або виконати `newgrp`.

### 4 Права доступу: три категорії, три дії

Права описують, що можуть робити з файлом власник (`u`), група-власник (`g`) та всі інші (`o`). Дії — читання (`r`), запис (`w`), виконання (`x`).

```
-rwxr-x---  1 dev1 developers  4096 вер 18 11:20 script.sh
│└┬┘└┬┘└┬┘     └┬─┘ └───┬────┘
│ │  │  │       │       └── група-власник
│ │  │  │       └────────── власник
│ │  │  └────────────────── права інших: немає
│ │  └───────────────────── права групи: читання й виконання
│ └──────────────────────── права власника: читання, запис, виконання
└────────────────────────── тип: - звичайний файл, d каталог, l посилання
```

Для каталогу права мають інший зміст: `r` дозволяє переглянути перелік імен, `w` — створювати й видаляти записи, `x` — увійти в каталог і звертатися до файлів усередині. Саме тому каталог без `x` недоступний навіть тоді, коли права на самі файли дозволяють доступ.

Таблиця 2 — Числове й символьне подання прав

| Числове | Символьне | Типове застосування |
|---------|-----------|---------------------|
| `644` | `rw-r--r--` | звичайний документ |
| `600` | `rw-------` | приватний файл, ключ, пароль |
| `755` | `rwxr-xr-x` | програма, скрипт, каталог загального доступу |
| `750` | `rwxr-x---` | каталог для власника й групи |
| `770` | `rwxrwx---` | спільний каталог команди |
| `777` | `rwxrwxrwx` | доступ усім: у робочих системах не застосовують |

```bash
chmod 750 script.sh                    # числовий спосіб
chmod u+x,g-w,o= script.sh             # символьний спосіб
chmod -R g+rX /srv/team                # рекурсивно, X лише для каталогів
sudo chown dev1:developers report.txt  # змінити власника й групу
sudo chgrp developers report.txt       # лише групу
```

Великий `X` у `chmod -R g+rX` додає право виконання тільки каталогам і тим файлам, у яких воно вже є хоча б для однієї категорії. Це стандартний прийом, щоб рекурсивна зміна прав не зробила виконуваними всі текстові файли.

### 5 Маска прав umask

Програма, що створює файл, запитує права `666` для файлів і `777` для каталогів, а маска `umask` вказує, які біти з них **прибрати**. Це побітова операція «і не», а не віднімання: для маски `027` віднімання дало б неможливе `639`, а справжній результат — `640`.

```bash
umask                                  # поточна маска: 0022 або 0002
umask -S                               # у символьному вигляді: u=rwx,g=rx,o=rx
touch a.txt && ls -l a.txt             # 666 без 022 = 644
mkdir d && ls -ld d                    # 777 без 022 = 755
umask 077                              # приватний режим: 600 і 700
```

В Ubuntu і Debian звичайний користувач отримує маску `0002`, а не `0022`: кожен має власну основну групу з тим самим іменем (схема user private group), тож право запису для групи нікому зайвому доступу не дає. Модуль `pam_umask` вмикає таку маску, коли ім'я користувача збігається з іменем його основної групи.

### 6 Спеціальні біти

Таблиця 3 — Спеціальні біти прав

| Біт | Числом | Для чого |
|-----|--------|----------|
| SUID | `4000` | програма виконується з правами власника файлу (`passwd`) |
| SGID | `2000` | на каталозі: нові файли успадковують групу каталогу |
| Sticky | `1000` | у спільному каталозі видаляти файл може лише його власник (`/tmp`) |

```bash
ls -l /usr/bin/passwd                  # -rwsr-xr-x  → SUID
ls -ld /tmp                            # drwxrwxrwt  → sticky
sudo chmod 2770 /srv/team              # SGID для спільного каталогу
sudo chmod +t /srv/team                # додати sticky
```

Комбінація SGID і sticky — класичний рецепт спільного каталогу команди: усі учасники групи можуть створювати файли, ці файли автоматично належать спільній групі, але видалити чужий файл ніхто не може.

### 7 Списки контролю доступу ACL

Класична модель описує права лише для трьох категорій. Коли потрібен доступ для окремого користувача поза групою, застосовують ACL.

```bash
getfacl report.txt                     # переглянути список
setfacl -m u:dev2:rw report.txt        # дати конкретному користувачу
setfacl -m g:testers:r report.txt      # дати конкретній групі
setfacl -x u:dev2 report.txt           # прибрати запис
setfacl -d -m g:developers:rwx /srv/team   # права за замовчуванням для нових файлів
```

Файл із ACL позначається знаком `+` у виводі `ls -l`: `-rw-rw-r--+`. Це перше, на що дивляться, коли права «за таблицею» виглядають правильно, а доступ поводиться інакше. Після першого запису ACL з'являється ще й **маска** (`mask::`) — верхня межа для всіх записів, крім власника та інших; саме її показує `ls -l` на місці прав групи. Якщо команд `getfacl` і `setfacl` немає, їх встановлює пакет `acl`.

## Приклад виконання

### Крок 1. Навчальні користувачі та група

Точний текст повідомлень `adduser` залежить від його версії; номери UID і GID у вас також можуть бути іншими.

```bash
student@lab-vm:~$ sudo adduser dev1 --gecos "Developer One" --disabled-password
info: Adding user `dev1' ...
info: Adding new group `dev1' (1001) ...
info: Creating home directory `/home/dev1' ...
info: Copying files from `/etc/skel' ...

student@lab-vm:~$ sudo adduser dev2 --gecos "Developer Two" --disabled-password
student@lab-vm:~$ sudo groupadd developers
student@lab-vm:~$ sudo usermod -aG developers dev1
student@lab-vm:~$ sudo usermod -aG developers dev2

student@lab-vm:~$ id dev1
uid=1001(dev1) gid=1001(dev1) groups=1001(dev1),1003(developers)

student@lab-vm:~$ getent group developers
developers:x:1003:dev1,dev2
```

Основна група `dev1` створена автоматично з тим самим іменем — така схема (user private group) унеможливлює випадковий спільний доступ через основну групу. Групу `developers` створено після користувачів навмисне: інакше вона зайняла б GID 1001, і номери UID та GID нових користувачів розійшлися б.

### Крок 2. Дослідження облікових записів

```bash
student@lab-vm:~$ grep -E "dev1|dev2" /etc/passwd
dev1:x:1001:1001:Developer One,,,:/home/dev1:/bin/bash
dev2:x:1002:1002:Developer Two,,,:/home/dev2:/bin/bash

student@lab-vm:~$ sudo grep dev1 /etc/shadow | cut -c1-40
dev1:!:20714:0:99999:7:::

student@lab-vm:~$ awk -F: '$3 < 1000 {print $1}' /etc/passwd | head -5
root
daemon
bin
sys
sync

student@lab-vm:~$ awk -F: '$3 >= 1000 && $3 < 65534 {print $1, $3}' /etc/passwd
student 1000
dev1 1001
dev2 1002
```

Знак оклику на місці хеша означає заблокований пароль: обліковий запис створено з `--disabled-password`, тож увійти за паролем неможливо. Число `20714` — дата останньої зміни пароля в днях від 1 січня 1970 року (тут — 18 вересня 2026-го), далі — мінімальний і максимальний строк дії пароля та за скільки днів попереджати.

### Крок 3. Права: символьний і числовий спосіб

```bash
student@lab-vm:~$ mkdir -p ~/lab8 && cd ~/lab8
student@lab-vm:~/lab8$ echo "echo Привіт" > script.sh
student@lab-vm:~/lab8$ ls -l script.sh
-rw-rw-r-- 1 student student 18 вер 18 11:15 script.sh

student@lab-vm:~/lab8$ ./script.sh
bash: ./script.sh: Permission denied

student@lab-vm:~/lab8$ chmod u+x script.sh
student@lab-vm:~/lab8$ ls -l script.sh
-rwxrw-r-- 1 student student 18 вер 18 11:15 script.sh

student@lab-vm:~/lab8$ ./script.sh
Привіт

student@lab-vm:~/lab8$ chmod 640 script.sh && ls -l script.sh
-rw-r----- 1 student student 18 вер 18 11:15 script.sh
```

Право на виконання перевіряється саме в момент запуску: файл зі скриптом лишається текстовим, але без біта `x` ядро відмовляється його запустити. Розмір 18 байтів, а не 12: кожна кирилична літера в UTF-8 займає два байти, плюс символ кінця рядка. Права `rw-rw-r--` у щойно створеного файлу — наслідок маски `0002`, про яку йдеться в кроці 5.

### Крок 4. Права каталогу

```bash
student@lab-vm:~/lab8$ mkdir secret && echo "дані" > secret/data.txt
student@lab-vm:~/lab8$ chmod 644 secret
student@lab-vm:~/lab8$ ls secret
ls: cannot access 'secret/data.txt': Permission denied
data.txt

student@lab-vm:~/lab8$ cat secret/data.txt
cat: secret/data.txt: Permission denied

student@lab-vm:~/lab8$ chmod 755 secret
student@lab-vm:~/lab8$ cat secret/data.txt
дані
```

Каталог без біта `x` дозволяє прочитати перелік імен, але не дозволяє звернутися до самих файлів — права на файл при цьому не змінювалися. Навіть `ls` показав ім'я `data.txt` з помилкою: ім'я він прочитав з каталогу (право `r`), а щоб розфарбувати вивід за типом файлу, спробував прочитати його inode — і отримав відмову (права `x` немає).

### Крок 5. Маска umask

```bash
student@lab-vm:~/lab8$ umask
0002
student@lab-vm:~/lab8$ touch default.txt && mkdir default.d
student@lab-vm:~/lab8$ ls -ld default.txt default.d
-rw-rw-r-- 1 student student    0 вер 18 11:22 default.txt
drwxrwxr-x 2 student student 4096 вер 18 11:22 default.d

student@lab-vm:~/lab8$ umask 077
student@lab-vm:~/lab8$ touch private.txt && mkdir private.d
student@lab-vm:~/lab8$ ls -ld private.txt private.d
-rw------- 1 student student    0 вер 18 11:23 private.txt
drwx------ 2 student student 4096 вер 18 11:23 private.d

student@lab-vm:~/lab8$ umask 002
```

Маска не змінює вже створені файли — вона діє лише на ті, що створюються після її встановлення, і лише в поточній оболонці та її дочірніх процесах.

### Крок 6. Спільний каталог команди

```bash
student@lab-vm:~/lab8$ sudo mkdir -p /srv/team
student@lab-vm:~/lab8$ sudo chown root:developers /srv/team
student@lab-vm:~/lab8$ sudo chmod 2770 /srv/team
student@lab-vm:~/lab8$ sudo chmod +t /srv/team
student@lab-vm:~/lab8$ ls -ld /srv/team
drwxrws--T 2 root developers 4096 вер 18 11:30 /srv/team

student@lab-vm:~/lab8$ sudo -u dev1 touch /srv/team/from-dev1.txt
student@lab-vm:~/lab8$ ls -l /srv/team
-rw-r--r-- 1 dev1 developers 0 вер 18 11:31 from-dev1.txt

student@lab-vm:~/lab8$ sudo -u dev2 rm /srv/team/from-dev1.txt
rm: cannot remove '/srv/team/from-dev1.txt': Operation not permitted
```

Файл, створений `dev1`, автоматично отримав групу `developers` — це дія біта SGID. Права файлу `rw-r--r--`, бо `sudo` запускає команду з маскою не м'якшою за `0022`. Спроба `dev2` видалити чужий файл відхилена бітом sticky, хоча права групи на каталог запис дозволяють. Велика `T` у `drwxrws--T` означає sticky-біт без права `x` для інших.

### Крок 7. Точковий доступ через ACL

```bash
student@lab-vm:~/lab8$ echo "звіт" > report.txt && chmod 640 report.txt
student@lab-vm:~/lab8$ sudo -u dev2 cat ~student/lab8/report.txt
cat: /home/student/lab8/report.txt: Permission denied

student@lab-vm:~/lab8$ setfacl -m u:dev2:r report.txt
student@lab-vm:~/lab8$ ls -l report.txt
-rw-r-----+ 1 student student 9 вер 18 11:40 report.txt

student@lab-vm:~/lab8$ getfacl -c report.txt
user::rw-
user:dev2:r--
group::r--
mask::r--
other::---

student@lab-vm:~/lab8$ ls -ld ~
drwxr-x--- 22 student student 4096 вер 18 11:38 /home/student
student@lab-vm:~/lab8$ sudo -u dev2 cat ~student/lab8/report.txt
cat: /home/student/lab8/report.txt: Permission denied

student@lab-vm:~/lab8$ chmod o+x ~
student@lab-vm:~/lab8$ sudo -u dev2 cat ~student/lab8/report.txt
звіт
student@lab-vm:~/lab8$ chmod o-x ~
```

Знак `+` у виводі `ls -l` — ознака ACL, а рядок `mask::r--` — верхня межа прав для записів ACL. Зверніть увагу: ACL на файлі не допоміг, доки `dev2` не міг пройти через домашній каталог `student` — з Ubuntu 21.04 домашні каталоги створюються з правами `750`. Право `x` на **кожен** каталог шляху обов'язкове незалежно від ACL. Наприкінці право відкликано, щоб не лишати домашній каталог відкритим.

2. Дослідити структуру `/etc/passwd`: пояснити призначення кожного поля на прикладі власного запису. Вивести окремо системні облікові записи (UID < 1000) і записи людей.

3. Створити групу та двох навчальних користувачів згідно з варіантом. Додати обох до створеної групи. Показати результат командами `id` і `getent group`.

4. Вивести відомості про терміни дії пароля одного з користувачів (`chage -l`) і заблокувати другий обліковий запис. Показати, як блокування відображається в `/etc/shadow`.

5. Створити каталог `~/lab8` з файлами та скриптом. Встановити права символьним способом, потім ті самі права — числовим. Показати, що результат однаковий.

6. Продемонструвати різницю прав для каталогу: зняти біт `x`, спробувати прочитати файл усередині, пояснити результат.

7. Дослідити маску `umask`: створити файл і каталог за поточної маски, змінити маску на значення свого варіанта, повторити й пояснити різницю.

8. Налаштувати спільний каталог команди `/srv/team` з бітами SGID і sticky. Від імені обох користувачів створити файли, потім спробувати видалити чужий файл. Пояснити результат кожної операції.

9. Надати доступ до файлу конкретному користувачеві через ACL згідно з варіантом. Показати вивід `getfacl` і пояснити, чому знадобилися права на батьківські каталоги.

10. Виконати додаткове завдання свого варіанта.

11. Прибрати за собою: повернути права домашнього каталогу (`chmod o-x ~`), видалити навчальних користувачів (`sudo deluser --remove-home dev1`) і групу (`sudo groupdel developers`), якщо це передбачено варіантом, і зафіксувати результат.

12. Оформити звіт і зробити висновок.

## Вимоги до звіту

Звіт оформлюється на бланку встановленого зразка і має містити:

- тему, мету та обладнання;
- постановку задачі за індивідуальним варіантом;
- опис полів `/etc/passwd` на прикладі створеного облікового запису;
- перелік виконаних команд із поясненням призначення кожного ключа;
- таблицю прав до і після кожної зміни (числове й символьне подання);
- знімки екрана, які підтверджують відмову в доступі та її усунення;
- пояснення дії бітів SGID і sticky за результатами пункту 8;
- відповідь на запитання додаткового завдання варіанта;
- висновок про те, чому модель «власник — група — інші» доповнюють списками ACL.

## Контрольні запитання

Запитання згруповано за рівнями навчальних досягнень. Для позитивної оцінки студент має відповісти на запитання середнього рівня, оцінка «добре» потребує відповідей достатнього рівня, оцінка «відмінно» — високого.

### Середній рівень (репродуктивний)

1. Які поля містить запис користувача у `/etc/passwd`?
2. Де зберігаються хеші паролів і хто має доступ до цього файлу?
3. Чим основна група відрізняється від додаткової?
4. Розшифруйте права `-rwxr-x---` у числовому вигляді.
5. Які команди змінюють власника й групу файлу?
6. Що робить команда `umask`?
7. Для чого призначений біт sticky?
8. Якою командою переглядають список ACL файлу?

### Достатній рівень (конструктивно-варіативний)

1. Чому ключ `-a` в `usermod -aG` критично важливий? Що станеться без нього?
2. Що означають права `r`, `w`, `x` для каталогу і чим цей зміст відрізняється від файлу?
3. Запишіть команду, яка рекурсивно дасть групі право читання, а виконання — лише каталогам.
4. Чому файл із правами `644` не запускається як скрипт і як це виправити?
5. Поясніть, як з маски `umask 027` виходять права `640` для нового файлу.
6. Навіщо на спільному каталозі команди встановлюють SGID?
7. Чому користувач із правом читання файлу все одно може отримати «Permission denied»?
8. Коли класичної моделі прав недостатньо і потрібні ACL?

### Високий рівень (творчий)

1. Спроєктуйте права для каталогу проєкту, у якому працюють дві групи: одна редагує файли, друга лише читає. Опишіть команди й обґрунтуйте кожне рішення.
2. Поясніть, навіщо програмі `passwd` потрібен біт SUID, які ризики це створює і як система їх обмежує.
3. Користувача видалено, а його файли залишилися. Опишіть, що станеться з цими файлами і чому, та запропонуйте коректний порядок видалення облікового запису.
4. Сформулюйте принцип найменших привілеїв і покажіть на трьох прикладах із цієї роботи, як він реалізується засобами прав доступу Linux.
