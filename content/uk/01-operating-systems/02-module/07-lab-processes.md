## Теоретичні відомості

### 1 Процес і його атрибути

Процес — програма, що виконується, разом з усім, що їй виділила ОС: адресним простором, відкритими файлами, потоками, правами. Кожен процес має ідентифікатор **PID** і знає PID свого батька **PPID**: процеси утворюють дерево з коренем у `systemd` (PID 1). Усе, що ядро знає про процес, доступно у віртуальному каталозі `/proc/PID`.

Таблиця 1 — Відомості про процес у /proc

| Файл | Що містить |
|------|------------|
| `/proc/PID/status` | ім'я, стан, PPID, UID, пам'ять (VmRSS), кількість потоків |
| `/proc/PID/cmdline` | командний рядок запуску (аргументи розділені нульовими байтами) |
| `/proc/PID/fd/` | відкриті файлові дескриптори — посилання на файли, сокети, канали |
| `/proc/PID/sched` | статистика планувальника: перемикання, vruntime |
| `/proc/PID/wchan` | функція ядра, в якій процес зараз чекає |

### 2 Стани процесів

```
┌───────────────────────────────────────────────────────────────────────┐
│                    СТАНИ ПРОЦЕСІВ (STAT у ps)                         │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│   ОСНОВНІ СТАНИ:                                                      │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │ R → Running    → виконується або готовий                        │ │
│   │ S → Sleeping   → очікує події (interruptible)                   │ │
│   │ D → Disk sleep → очікує I/O (uninterruptible)                   │ │
│   │ T → Stopped    → зупинений (Ctrl+Z або SIGSTOP)                 │ │
│   │ Z → Zombie     → завершений, чекає wait() від батька            │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   ДОДАТКОВІ СИМВОЛИ:                                                  │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │ < → high priority (low nice)                                    │ │
│   │ N → low priority (high nice)                                    │ │
│   │ s → session leader                                              │ │
│   │ l → multi-threaded (uses CLONE_THREAD)                          │ │
│   │ + → foreground process group                                    │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   ПРИКЛАДИ:                                                           │
│   Ss  → sleeping, session leader                                      │
│   R+  → running, foreground                                           │
│   SN  → sleeping, nice (low priority)                                 │
│   Sl  → sleeping, multi-threaded                                      │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

Літера `R` у Linux означає і «виконується», і «готовий до виконання»: ядро не розрізняє ці стани. Процес у стані `D` чекає всередині драйвера й не реагує навіть на SIGKILL, доки операція не завершиться.

### 3 Сигнали

Сигнал — коротке асинхронне повідомлення процесу від ядра або іншого процесу. На більшість сигналів програма може встановити власний обробник або ігнорувати їх; SIGKILL і SIGSTOP перехопити неможливо — їх виконує саме ядро.

Таблиця 2 — Основні сигнали

| Сигнал | Номер | Типова дія | Звідки береться |
|--------|-------|------------|-----------------|
| SIGHUP | 1 | завершення; служби перечитують конфігурацію | закриття терміналу, `kill -HUP` |
| SIGINT | 2 | завершення | Ctrl+C |
| SIGKILL | 9 | негайне завершення, не перехоплюється | `kill -9` |
| SIGTERM | 15 | коректне завершення | `kill` без ключа, `systemctl stop` |
| SIGCONT | 18 | продовжити зупинений процес | `kill -CONT`, `fg`, `bg` |
| SIGSTOP | 19 | зупинка, не перехоплюється | `kill -STOP` |
| SIGTSTP | 20 | зупинка з терміналу, перехоплюється | Ctrl+Z |

Правило завершення процесу: спершу SIGTERM і кілька секунд очікування, щоб програма зберегла дані й закрила файли, і лише потім SIGKILL.

### 4 Керування завданнями в оболонці

Команда із символом `&` у кінці виконується у **фоні**: оболонка одразу повертає запрошення, а PID останнього фонового процесу зберігає в змінній `$!`. Команда `jobs` показує фонові й зупинені завдання, `fg %N` повертає завдання на передній план, `bg %N` продовжує зупинене завдання у фоні. Ctrl+Z надсилає процесу переднього плану сигнал SIGTSTP.

У підоболонці `( … )` змінна `$$` лишається PID-ом головного скрипта: так визначено в POSIX. Власний PID підоболонки в bash — змінна `$BASHPID`.

### 5 Пріоритети

Значення **nice** (від −20 до +19) задає вагу процесу для планувальника: кожен крок змінює частку процесорного часу приблизно в 1,25 раза. Збільшити nice (стати «поступливішим») може будь-хто, зменшити — лише root. Колонка `PRI` у `ps -o pri` — похідне значення для відображення, а не те, що безпосередньо використовує планувальник.

Вплив nice видно, лише коли процеси **змагаються за одне ядро**. На восьмиядерному процесорі три задачі з різним nice отримають по 100 % кожна, бо ядер вистачає всім. Тому в експериментах процеси прив'язують до одного ядра командою `taskset -c 0`.

### 6 Зомбі й сироти

**Зомбі** — процес, що завершився, але батько ще не прочитав його код повернення викликом `wait()`. Зомбі не займає пам'яті програми, але тримає запис у таблиці процесів і PID. Прибрати його можна лише через батька: змусити його викликати `wait()` або завершити — тоді зомбі перейде до нового батька, який його прибере.

**Сирота** — процес, чий батько завершився раніше. Сироту «всиновлює» не завжди PID 1: процес може оголосити себе **subreaper**-ом (`prctl(PR_SET_CHILD_SUBREAPER)`), і тоді сироти з його піддерева переходять до нього. У графічному сеансі Ubuntu таким є `systemd --user`, тож новим батьком сироти з вашого терміналу стане саме він.

### 7 Процеси у Windows

У Windows процес також має PID і пам'ятає PID батька, але дерево не підтримується: після завершення батька дитина лишається зі «старим» PPID, а сиріт ніхто не всиновлює. Сигналів немає: команда `taskkill` без ключа `/f` надсилає вікнам програми повідомлення WM_CLOSE, а з `/f` — викликає TerminateProcess. Пріоритет задає клас процесу: Idle, BelowNormal, Normal, AboveNormal, High, RealTime.

Таблиця 3 — Відповідність команд Linux і Windows

| Дія | Linux | Windows (PowerShell / CMD) |
|-----|-------|----------------------------|
| Перелік процесів | `ps aux` | `Get-Process`, `tasklist` |
| Батьківський процес | `ps -o ppid= -p PID` | `Get-CimInstance Win32_Process -Filter "ProcessId=PID"` → ParentProcessId |
| Завершити коректно | `kill PID` | `taskkill /pid PID` |
| Завершити примусово | `kill -9 PID` | `Stop-Process -Id PID -Force`, `taskkill /f /pid PID` |
| Змінити пріоритет | `renice 10 -p PID` | `(Get-Process -Id PID).PriorityClass = 'BelowNormal'` |
| Монітор у реальному часі | `top`, `htop` | диспетчер задач, `resmon` |

## Приклад виконання

Номери PID, кількість процесів і відсотки CPU у вас будуть іншими — у звіт вносяться ваші результати.

### Крок 1. Підготовка середовища

```bash
sudo apt update
sudo apt install -y htop stress-ng psmisc      # psmisc — pstree, killall
mkdir -p ~/lab11 && cd ~/lab11

# Навантаження на процесор: порожній нескінченний цикл
cat > cpu_load.sh << 'EOF'
#!/bin/bash
echo "cpu_load: PID $$"
while :; do :; done
EOF

# Батько з трьома дочірніми процесами
cat > parent_child.sh << 'EOF'
#!/bin/bash
echo "Батько: PID $$"
for i in 1 2 3; do
    (
        # $$ у підоболонці — PID батька; власний PID — $BASHPID
        echo "Дитина $i: PID $BASHPID, батько $(ps -o ppid= -p $BASHPID)"
        sleep 300
    ) &
done
wait
EOF
chmod +x cpu_load.sh parent_child.sh
```

### Крок 3. Фонові завдання, Ctrl+Z і сигнали STOP/CONT

```bash
student@lab-vm:~/lab11$ ./cpu_load.sh
cpu_load: PID 5210
^Z
[1]+  Stopped                 ./cpu_load.sh
student@lab-vm:~/lab11$ ps -o pid,stat,pcpu,comm -p 5210
    PID STAT %CPU COMMAND
   5210 T    52.4 cpu_load.sh
student@lab-vm:~/lab11$ bg %1
[1]+ ./cpu_load.sh &
student@lab-vm:~/lab11$ kill -STOP 5210; ps -o stat= -p 5210
T
student@lab-vm:~/lab11$ kill -CONT 5210; ps -o stat= -p 5210
R

```

Стан `T` означає зупинений процес. Колонка `%CPU` у `ps` — середнє за весь час життя процесу, тому одразу після зупинки вона ще не нульова.

### Крок 4. SIGTERM проти SIGKILL

```bash
student@lab-vm:~/lab11$ cat > stubborn.sh << 'EOF'
#!/bin/bash
trap 'echo "SIGTERM проігноровано"' TERM
echo "stubborn: PID $$"
while :; do sleep 1; done
EOF
student@lab-vm:~/lab11$ chmod +x stubborn.sh && ./stubborn.sh &
stubborn: PID 5301
student@lab-vm:~/lab11$ kill 5301
SIGTERM проігноровано
student@lab-vm:~/lab11$ kill -9 5301
[1]+  Killed                  ./stubborn.sh
```

Обробник `trap` перехопив SIGTERM, і програма продовжила роботу. SIGKILL перехопити неможливо: його виконує ядро, не питаючи програму, — тому незбережені дані програми втрачаються.

### Крок 5. Пріоритети на одному ядрі

```bash
student@lab-vm:~/lab11$ taskset -c 0 ./cpu_load.sh > /dev/null &
student@lab-vm:~/lab11$ taskset -c 0 nice -n 10 ./cpu_load.sh > /dev/null &
student@lab-vm:~/lab11$ sleep 20; top -b -n 1 -p "$(pgrep -d, cpu_load)" | tail -3
    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   5402 student   20   0    7372   3456   3200 R  91.0   0.1   0:18.20 cpu_load.sh
   5403 student   30  10    7372   3456   3200 R   9.0   0.1   0:01.81 cpu_load.sh

student@lab-vm:~/lab11$ renice 0 -p 5403

student@lab-vm:~/lab11$ pkill cpu_load
```

Обидва процеси прив'язано до ядра 0, тому вони змагаються за нього: процес з nice 10 отримує приблизно 10 %, як і передбачає співвідношення ваг 1024 : 110. Повернути nice до 0 без sudo не можна — зменшення значення nice дозволене лише root.

### Крок 6. Зомбі та сирота

```bash
student@lab-vm:~/lab11$ bash -c 'sleep 1 & exec sleep 60' &
[1] 5501
student@lab-vm:~/lab11$ sleep 2; ps -o pid,ppid,stat,cmd --ppid 5501
    PID    PPID STAT CMD
   5502    5501 Z    [sleep] <defunct>
```

Оболонка запустила дитину `sleep 1`, а потім командою `exec` замінила себе програмою `sleep 60`, яка не викликає `wait()`. Дитина завершилася й стала зомбі. Коли `sleep 60` завершиться (або отримає `kill 5501`), зомбі перейде до нового батька й зникне.

```bash
student@lab-vm:~/lab11$ bash -c 'sleep 120 & echo "дитина $!"; exit'
дитина 5610
student@lab-vm:~/lab11$ ps -o pid,ppid,cmd -p 5610
    PID    PPID CMD
   5610    1873 sleep 120
student@lab-vm:~/lab11$ ps -o pid,cmd -p 1873
    PID CMD
   1873 /usr/lib/systemd/systemd --user
```

Батько завершився одразу, і сирота `sleep 120` отримала нового батька — не PID 1, а `systemd --user`, який оголосив себе subreaper-ом. На сервері без графічного сеансу новим батьком зазвичай стає PID 1.

## Порядок виконання роботи

1. Отримати в викладача номер індивідуального варіанта.

2. Підготувати середовище: встановити утиліти `htop`, `pstree`, `stress-ng`, створити каталог `~/lab11` і навчальні скрипти згідно з кроком 1.

3. Отримати перелік процесів трьома способами — `ps`, `ps aux`, `ps -ef` — і пояснити різницю у складі колонок.

4. Побудувати дерево процесів командою `pstree` і визначити, який процес породив ваш термінал. Запустити `parent_child.sh` і пояснити, чому для PID дитини використано `$BASHPID`, а не `$$`.

5. Знайти процес, зазначений у варіанті, визначити його PID, PPID, стан, пріоритет та обсяг зайнятої пам'яті (з `ps` і з `/proc/PID/status`).

6. Запустити навчальний скрипт у фоновому режимі, перевести його на передній план і назад, зупинити й продовжити сигналами SIGSTOP/SIGCONT, після чого завершити сигналом, зазначеним у варіанті.

7. Порівняти дію сигналів SIGTERM і SIGKILL на процесі, що перехоплює SIGTERM. Зафіксувати, у чому полягає різниця.

8. Запустити на одному ядрі (`taskset -c 0`) два процеси навантаження, один із пріоритетом свого варіанта, і порівняти їхні частки CPU. Змінити пріоритет уже запущеного процесу командою `renice` і пояснити, чому зменшення значення потребує прав root.

9. Відтворити зомбі- та осиротілий процес за кроком 6. Зафіксувати стан процесу у виводі `ps` і визначити, який процес став батьком сироти у вашій системі.

10. Виконати в Windows перегляд процесів, визначення батьківського процесу, зміну класу пріоритету й завершення процесу за кроком 7.

11. Виконати індивідуальне завдання свого варіанта.

12. Оформити звіт і зробити висновок.

## Вимоги до звіту

Звіт оформлюється на бланку встановленого зразка і має містити:

- тему, мету та обладнання;
- постановку задачі за індивідуальним варіантом;
- таблицю з переліком досліджених процесів: PID, PPID, стан, пріоритет, пам'ять;
- перелік виконаних команд із поясненням призначення кожного ключа;
- знімки екрана з результатами кожного кроку, зокрема вивід `pstree`, стан зомбі-процесу й частки CPU за різних nice;
- порівняння дії сигналів SIGTERM і SIGKILL;
- порівняння засобів керування процесами в Linux і Windows за результатами кроку 7;
- текст і результат роботи скрипта індивідуального завдання;
- висновок про те, якими засобами адміністратор діагностує та усуває проблеми з процесами.

## Контрольні запитання

Запитання згруповано за рівнями навчальних досягнень. Для позитивної оцінки студент має відповісти на запитання середнього рівня, оцінка «добре» потребує відповідей достатнього рівня, оцінка «відмінно» — високого.

### Середній рівень (репродуктивний)

1. Що таке процес і які ресурси виділяє йому операційна система?
2. Яка різниця між `ps aux` та `ps -ef`? Які колонки відрізняються?
3. Назвіть основні стани процесу в Linux і позначення кожного у виводі `ps`.
4. Поясніть різницю між SIGTERM (15) та SIGKILL (9).
5. Що таке nice value і в яких межах він змінюється?
6. Що таке zombie-процес і як він виникає?
7. Чим foreground-процес відрізняється від background-процесу? Як перемикати режим?
8. Як дізнатися, скільки потоків має процес?

### Достатній рівень (конструктивно-варіативний)

1. Що означає стан «D» (disk sleep) і чому такий процес не завершується командою `kill -9`?
2. Чому для зменшення значення nice потрібні права root, а для збільшення — ні?
3. Як «видалити» zombie-процес, якщо сам він уже не виконується?
4. Що відбувається з дочірніми процесами, коли батьківський процес завершується раніше за них?
5. Запишіть команду, яка покаже п'ять процесів з найбільшим споживанням пам'яті.
6. Чим `kill`, `pkill` і `killall` відрізняються за способом вибору процесу?
7. Як подивитися дерево процесів і визначити, який процес породив заданий?
8. Які відомості про процес дає каталог `/proc/PID` і чим він зручніший за `ps`?

### Високий рівень (творчий)

1. Процес не реагує ні на SIGTERM, ні на SIGKILL. Назвіть можливі причини та порядок дій адміністратора.
2. Сервер періодично «підвисає» під навантаженням. Опишіть, які показники процесів ви перевірите й у якій послідовності.
3. Поясніть, чому кількість zombie-процесів, що зростає, є ознакою помилки в програмі, а не в ядрі.
4. Сформулюйте критерій, за яким адміністратор обирає між зміною пріоритету процесу та його завершенням. Проілюструйте прикладом.
